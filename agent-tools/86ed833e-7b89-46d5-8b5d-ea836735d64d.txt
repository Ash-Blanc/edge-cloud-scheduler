$$$[0,\\mathit{num\\_layers})$$$</td></tr></tbody></table></p><p><span class=\"tex-font-style-bf\">The Problem in One Minute</span></p><p>One <span class=\"tex-font-style-bf\">local computer</span> and several <span class=\"tex-font-style-bf\">remote computers</span> handle requests. Each request first prepares its input by making this trip:</p><p>$$$$$$\\text{local computer} \\longrightarrow \\text{remote computer} \\longrightarrow \\text{local computer}.$$$$$$ </p><p>The same trip is then repeated once per token. The first trip is the <span class=\"tex-font-style-bf\">input stage</span>; each later trip is an <span class=\"tex-font-style-bf\">output step</span>. Transfers are automatic; you choose ready tasks for free computers.</p><p>The score rewards output rate and short waits. <span class=\"tex-font-style-bf\">Time to decode ready (TDR)</span> ends when the first output step can begin, before a token is produced. <span class=\"tex-font-style-bf\">Time per output token (TPOT)</span> is the mean gap between consecutive tokens.</p><p><span class=\"tex-font-style-bf\">Challenge Format</span></p><p>Two worked examples appear at the end of the statement. Test 1 is the public worked Example 1, tests 2–22 are hidden preliminary tests, and finals use a separate frozen set. Per-test scores are reported on the 0–1000 scale defined below, and the contest system aggregates them according to the contest rules; no hacks are used.</p><center> <img class=\"tex-graphics\" src=\"https://espresso.codeforces.com/43170ae33b5e5831954b4e6e82627c3a8c472687.png\" style=\"max-width: 100.0%;max-height: 100.0%;\" width=\"605px\"/> </center><p><span class=\"tex-font-style-it\">Guide:</span> blue is local, green is the shared two-way link, and orange is remote; computation and transfer may overlap. Figure labels use the glossary above.</p><p><span class=\"tex-font-style-bf\">What You Control</span></p><p>You choose:</p><ul> <li> which legal task to start on each free computer; </li><li> the remote computer assigned to a request when scheduling its <span class=\"tex-font-style-bf\">P PRE</span>; </li><li> how to split an input-stage <span class=\"tex-font-style-bf\">P PROC</span> into ranges of numbered parts; and </li><li> which ready requests to combine into each output group. </li></ul><p>Transfers are automatic. For a first solution, use one full input-stage piece and groups of size $$$1$$$.</p><p><span class=\"tex-font-style-bf\">System Model</span></p><ul> <li> There is <span class=\"tex-font-style-bf\">one local computer</span> and <span class=\"tex-font-style-bf\">$$$K$$$ identical remote computers</span>, numbered $$$0$$$ through $$$K-1$$$ and written <span class=\"tex-font-style-bf\">C0</span>, <span class=\"tex-font-style-bf\">C1</span>, $$$\\dots$$$. They work independently and may run while data moves. </li><li> There are $$$R$$$ requests in total, but $$$R$$$ is not announced. Request ids are $$$i=0,1,\\dots,R-1$$$ in arrival order. The arrival time of request $$$i$$$ is the timestamp of its <span class=\"tex-font-style-bf\">ARR</span> event. That event reveals its input length $$$L_{\\mathrm{in}}[i]$$$; its output length $$$L_{\\mathrm{out}}[i]$$$ remains hidden until a <span class=\"tex-font-style-bf\">FIN</span> event reports that it has finished. </li><li> Request $$$i$$$ performs one token-free <span class=\"tex-font-style-bf\">input stage</span>, then exactly $$$L_{\\mathrm{out}}[i]$$$ <span class=\"tex-font-style-bf\">output steps</span>, each producing one token. Thus total generated tokens are $$$\\sum_i L_{\\mathrm{out}}[i]$$$, with $$$L_{\\mathrm{out}}[i] \\ge 1$$$. </li><li> You assign each request to one remote computer in its <span class=\"tex-font-style-bf\">P PRE</span> task. The choice is fixed: all later input stage tasks for that request name the same remote computer, and every <span class=\"tex-font-style-bf\">D PROC</span> containing it runs there. Output-step tasks on the local computer may combine requests from different remote computers. </li><li> Each computer executes at most one task at a time. Once a task starts, it cannot be paused. Separately scheduled input-stage pieces may be alternated with other work. </li><li> <span class=\"tex-font-style-bf\">Schedule cost $$$S$$$</span>: a task assigned at time $$$t$$$ with execution duration $$$\\mathit{dur}$$$ occupies its computer over $$$[t,\\, t + S + \\mathit{dur}]$$$. The cost is paid once per task, including once per input-stage piece and once per output group. Transfers do not pay $$$S$$$. </li><li> <span class=\"tex-font-style-bf\">Execution times are fixed</span>: task duration depends on its step and group size (and fraction of parts for input-stage pieces), never on the output-token position or saved internal data size. See <span class=\"tex-font-style-bf\">Input</span> — <span class=\"tex-font-style-bf\">Task-Time Table</span>. Finished tasks and transfers are reported as <span class=\"tex-font-style-bf\">TDN</span> and <span class=\"tex-font-style-bf\">XDN</span>. </li></ul><p><span class=\"tex-font-style-bf\">Request Lifecycle</span></p><p>Solid arrows are scheduling dependencies; dashed arrows are automatic transfers.</p><center> <img class=\"tex-graphics\" src=\"https://espresso.codeforces.com/4a23fd401894e246799d4cbff754ffca382e02f3.png\" style=\"max-width: 100.0%;max-height: 100.0%;\" width=\"605px\"/> </center><p><span class=\"tex-font-style-it\">Guide:</span> TDR ends at <span class=\"tex-font-style-bf\">P POST</span>; each later <span class=\"tex-font-style-bf\">D POST</span> makes one token.</p><p><span class=\"tex-font-style-bf\">PRE</span>/<span class=\"tex-font-style-bf\">POST</span> use the local computer; <span class=\"tex-font-style-bf\">PROC</span> uses the assigned remote; transfers use the shared link.</p><p><span class=\"tex-font-style-bf\">Input Stage</span></p><p>Three steps: <span class=\"tex-font-style-bf\">first</span> (local) $$$\\to$$$ <span class=\"tex-font-style-bf\">process</span> (assigned remote) $$$\\to$$$ <span class=\"tex-font-style-bf\">final</span> (local). An input-stage group has one request.</p><ul> <li> <span class=\"tex-font-style-bf\">P PRE</span> (local computer). May start after: the request's <span class=\"tex-font-style-bf\">ARR</span> event. Fixes the remote computer; on completion, the local-to-remote transfer is queued immediately (whether or not that remote computer is busy). </li><li> <span class=\"tex-font-style-bf\">P PROC</span> (remote computer) computes all $$$\\mathit{num\\_layers}$$$ numbered parts. The simplest choice is one full piece $$$[0,\\,\\mathit{num\\_layers})$$$. You may split it so other remote work can run between pieces. </li><li> <span class=\"tex-font-style-bf\">P POST</span> (local computer). May start after: the request's input stage remote-to-local transfer <span class=\"tex-font-style-bf\">XDN</span>. Completion makes the request ready for producing output; <span class=\"tex-font-style-bf\">TDR</span> is measured from arrival to this completion. </li></ul><p><span class=\"tex-font-style-bf\">Exact splitting rules.</span> Each piece is a nonempty integer range $$$[ls,\\,le)$$$: it includes part $$$ls$$$ and stops before part $$$le$$$. For each request, pieces must be issued in ascending, gap-free order: the first starts at $$$0$$$, each later $$$ls$$$ equals the previous $$$le$$$, and the last ends at $$$\\mathit{num\\_layers}$$$. Thus there are at most $$$\\mathit{num\\_layers}$$$ pieces, and none when $$$\\mathit{num\\_layers}=1$$$ beyond the full piece. The first piece waits for the input stage local-to-remote transfer <span class=\"tex-font-style-bf\">XDN</span>; each later piece waits for the previous piece's <span class=\"tex-font-style-bf\">TDN</span>. Its duration is</p><p>$$$$$$\\frac{le-ls}{\\mathit{num\\_layers}}\\times \\mathit{prefill\\_proc}(L_{\\mathrm{in}}[i]).$$$$$$</p><p>Only the last piece queues the input stage remote-to-local transfer, of length $$$L_{\\mathrm{in}}[i]$$$. No transfer occurs between pieces. Any range that is empty, outside the part interval, out of order, or leaves a gap is a violation.</p><p><span class=\"tex-font-style-bf\">Output Steps</span></p><p>After the input stage, request $$$i$$$ performs $$$L_{\\mathrm{out}}[i]$$$ output steps in succession: completing iteration $$$k$$$'s final step readies iteration $$$k+1$$$. The same three steps are used, but multiple requests may be grouped per step. You choose each group independently. Output-step tasks cannot be split into part ranges.</p><ul> <li> <span class=\"tex-font-style-bf\">D PRE</span> (local computer, across remote computers): may group requests assigned to any mix of remote computers — the listed $$$\\mathit{decode\\_pre}$$$ time depends only on total group size, so across remote computers grouping improves local computer efficiency (the task-time table plus the transfer formula is the <span class=\"tex-font-style-bf\">only</span> efficiency model; nothing else rewards grouping). May start after, for each request: completion of that request's previous final step (<span class=\"tex-font-style-bf\">P POST</span> for its first output step, otherwise its previous <span class=\"tex-font-style-bf\">D POST</span>) — and the request must not be finished (<span class=\"tex-font-style-bf\">FIN</span> always arrives with the final <span class=\"tex-font-style-bf\">D POST</span> <span class=\"tex-font-style-bf\">TDN</span>, so you always know). Completion queues one local-to-remote transfer per distinct remote computer in the group (len $$$=$$$ that remote computer's member count), enqueued simultaneously in increasing remote computer index order. </li><li> <span class=\"tex-font-style-bf\">D PROC</span> (remote computer): all members must be assigned to that remote computer. May start after, for each request: the local-to-remote transfer <span class=\"tex-font-style-bf\">XDN</span> carrying that member's current-iteration data — the rule is checked <span class=\"tex-font-style-bf\">separately for each request</span>: members may come from different <span class=\"tex-font-style-bf\">D PRE</span> groups and different local-to-remote transfers. Completion queues one remote-to-local transfer (len $$$=$$$ this group's size). </li><li> <span class=\"tex-font-style-bf\">D POST</span> (local computer, across remote computers). May start after, for each request: the remote-to-local transfer <span class=\"tex-font-style-bf\">XDN</span> carrying that member's current-iteration result (different <span class=\"tex-font-style-bf\">D PROC</span> groups/remote-to-local transfers are fine). Each member's completion produces one token. </li></ul><center> <img class=\"tex-graphics\" src=\"https://espresso.codeforces.com/168f09de3ea9898d510022a86b0ea8200107975d.png\" style=\"max-width: 100.0%;max-height: 100.0%;\" width=\"605px\"/> </center><p><span class=\"tex-font-style-it\">Guide:</span> the upper lane splits one input stage into consecutive ranges; the lower lane groups ready requests for output.</p><p>Groups: $$$m \\ge 1$$$, request ids distinct, every member satisfying its predecessor rule; $$$m = 1$$$ is always allowed. Only output work is ever grouped — input-stage groups always contain exactly one request. <span class=\"tex-font-style-bf\">There is no other group-size limit</span>: no maximum exists or is announced — any nonempty set of distinct, currently ready requests may be grouped, subject only to the step and remote computer rules above. Order of request ids within a group: see Output.</p></div><div class=\"input-specification\"><div class=\"section-title\">Input</div><p><span class=\"tex-font-style-bf\">Protocol Guide</span></p><p><span class=\"tex-font-style-bf\">P</span> is the one-time input stage; <span class=\"tex-font-style-bf\">D</span> is one output step. <span class=\"tex-font-style-bf\">PRE</span>/<span class=\"tex-font-style-bf\">POST</span> are local tasks and <span class=\"tex-font-style-bf\">PROC</span> is remote. Events are <span class=\"tex-font-style-bf\">ARR</span> (arrival), <span class=\"tex-font-style-bf\">TDN</span> (task done), <span class=\"tex-font-style-bf\">XDN</span> (transfer done), and <span class=\"tex-font-style-bf\">FIN</span> (finished). In $$$[ls,le)$$$, $$$ls$$$ is included and $$$le$$$ excluded. Input arrives interactively: read each whole frame and respond once. Times are real milliseconds; counts, lengths, and ids are integers; fields use single spaces.</p><p><span class=\"tex-font-style-bf\">Startup Configuration</span></p><p>The interactor first sends two lines (no response expected): the system parameters, then the scoring parameters:</p><pre class=\"verbatim\"><br/>K S latency_in_ms bandwidth_gbps bytes_per_token num_layers<br/>SLO1 SLO2 tp_UB tp_base dist_base w_tp w_c<br/></pre><p>$$$K$$$, $$$\\mathrm{bytes\\_per\\_token}$$$, and $$$\\mathrm{num\\_layers}$$$ are integers; all other values are reals (times in ms, output rates in tokens/ms). <span class=\"tex-font-style-bf\">SLO</span> stands for service-level objective: <span class=\"tex-font-style-bf\">SLO1</span> is the TDR target and <span class=\"tex-font-style-bf\">SLO2</span> is the TPOT target. The other names on the scoring line mean: <span class=\"tex-font-style-bf\">tp_UB</span> $$$= tp_{\\mathrm{UB}}$$$, <span class=\"tex-font-style-bf\">tp_base</span> $$$= tp_{\\mathrm{base}}$$$, <span class=\"tex-font-style-bf\">dist_base</span> $$$= dist_{\\mathrm{base}}$$$, <span class=\"tex-font-style-bf\">w_tp</span> $$$= w_{\\mathrm{tp}}$$$, <span class=\"tex-font-style-bf\">w_c</span> $$$= w_c$$$. $$$\\mathrm{bandwidth\\_gbps}$$$ is in <span class=\"tex-font-style-bf\">gigabits per second (Gb/s)</span>. The value $$$\\mathrm{bytes\\_per\\_token}$$$ is already the complete data size for one token; do not multiply it by an element width.</p><p><span class=\"tex-font-style-bf\">Communication</span></p><p>Transfers are <span class=\"tex-font-style-bf\">automatic</span>: the interactor queues them when their triggering computation finishes; you never output a transfer command. A <span class=\"tex-font-style-bf\">single link</span> connects the local computer and remote computer side and is shared by all remote computers. <span class=\"tex-font-style-bf\">UP</span> means a local-to-remote transfer (local computer $$$\\to$$$ remote computer), and <span class=\"tex-font-style-bf\">DOWN</span> means a remote-to-local transfer (remote computer $$$\\to$$$ local computer). These are independent one-at-a-time FIFO queues: transfers finish in the order they enter, and both directions may be active simultaneously. For simultaneous queues, one <span class=\"tex-font-style-bf\">D PRE</span>'s per-remote transfers enter by increasing remote index. Otherwise transfers enter in interactor event order; tasks started together and finishing together use assignment-line order.</p><p>Transfer time $$$= \\mathrm{latency\\_in\\_ms} + 8\\,\\mathrm{data\\_bytes}/(\\mathrm{bandwidth\\_gbps}\\times10^6)$$$ ms, where $$$\\mathrm{data\\_bytes}=\\mathrm{len}\\times\\mathrm{bytes\\_per\\_token}$$$. The factor $$$8$$$ converts bytes to bits. For an input-stage transfer of request $$$i$$$, $$$\\mathrm{len}=L_{\\mathrm{in}}[i]$$$; for output, use the per-remote computer local-to-remote transfer and per-group remote-to-local transfer sizes defined in <span class=\"tex-font-style-bf\">Output Steps</span>. Guaranteed $$$\\mathrm{latency\\_in\\_ms}  \\gt  0$$$: every transfer takes strictly positive time.</p><p><span class=\"tex-font-style-bf\">Task-Time Table</span></p><p>Before requests arrive, the judge gives you a table telling you how long tasks take, in milliseconds. You only read this table; you do not measure the times yourself. Read an integer $$$N$$$, then $$$N$$$ rows of 7 values; no response is expected:</p><pre class=\"verbatim\"><br/>batch_size  prefill_pre  prefill_proc  prefill_post  decode_pre  decode_proc  decode_post<br/></pre><p>Here <span class=\"tex-font-style-bf\">batch_size</span> means the number of requests grouped into one task. The names containing <span class=\"tex-font-style-bf\">prefill</span> refer to the input stage, and the names containing <span class=\"tex-font-style-bf\">decode</span> refer to output steps. These fixed names come from the protocol; no AI knowledge is required. The values help you compare scheduling choices. You must read all rows, but a first correct scheduler does not need to use the values at all; a more advanced scheduler will use the complete task-time table, including values between listed rows.</p><p><span class=\"tex-font-style-bf\">batch_size</span> means $$$L_{\\mathrm{in}}$$$ for the three input stage columns (one request per input stage group) and member count for the three output columns. The <span class=\"tex-font-style-bf\">batch_size</span> values are distinct positive integers in $$$[1,4096]$$$. A listed output-step group size may exceed the test's $$$R$$$; such a row only defines the task-time table and does not make that group size schedulable. Not every step is listed at every group size; a missing value is <span class=\"tex-font-style-bf\">-1</span>. Rows are given in no guaranteed order. <span class=\"tex-font-style-bf\">Guarantee</span>: every step column contains at least one non-missing entry.</p><p>All listed values are <span class=\"tex-font-style-bf\">execution durations excluding the schedule cost $$$S$$$</span>, exactly like the <span class=\"tex-font-style-bf\">dur</span> field of every <span class=\"tex-font-style-bf\">TDN</span>: the total time for which a computer is busy with a task is always $$$S + \\mathit{dur}$$$ (see System Model). For each step, sort the available rows by group size. If the needed size is listed, use its time. If it lies between two listed sizes, draw a straight line between their times and use the value on that line. Below the smallest size, use the first time; above the largest size, use the last time. The result is the same on every remote computer and never changes. <span class=\"tex-font-style-bf\">Guarantee</span>: every resulting legal task duration is strictly positive. Here $$$R$$$ is the test's total request count (see Constraints); $$$R$$$ is <span class=\"tex-font-style-bf\">not announced</span> during the interaction and is not a separate group-size limit. No maximum output group size exists beyond the number of currently ready requests. The duration of every completed task is echoed in its <span class=\"tex-font-style-bf\">TDN</span>'s <span class=\"tex-font-style-bf\">dur</span> field.</p><p><span class=\"tex-font-style-bf\">Event Frames (Your Turns)</span></p><p>The interactor sends a frame whenever one or more events occur. A frame contains: one timestamp line <span class=\"tex-font-style-bf\">t</span>, one event-count line <span class=\"tex-font-style-bf\">e</span>, then $$$e$$$ event lines. Always read the whole frame before deciding what to do.</p><p>The frame timestamp is its event time, printed with 9 decimal places; printed timestamps are nondecreasing, while the internal event times of consecutive frames are strictly increasing. Only events with exactly the same internal timestamp are coalesced. A later event is never moved to an earlier frame, and line order carries no scheduling priority. Your response may use <span class=\"tex-font-style-underline\">any</span> event in the frame: every resource freed by a <span class=\"tex-font-style-bf\">TDN</span> is free, even if that event is the last line. Guarantee: <span class=\"tex-font-style-bf\">FIN</span> appears beside the <span class=\"tex-font-style-bf\">TDN</span> of that request's final output final step. After reading such a frame, the request is finished and must not appear in your response to that frame or any later response.</p><center> <img class=\"tex-graphics\" src=\"https://espresso.codeforces.com/70b44015079f4bd0cccaa0a4f3aa7467c0c6432f.png\" style=\"max-width: 100.0%;max-height: 100.0%;\" width=\"605px\"/> </center><p><span class=\"tex-font-style-it\">Guide:</span> read the whole event frame, update state, then print one count and exactly that many assignments.</p><ul> <li> <span class=\"tex-font-style-bf\">ARR &lt;rid&gt; &lt;$$$L_{\\mathrm{in}}[i]$$$&gt;</span> — request $$$i=\\textbf{rid}$$$ arrived; its arrival time is this frame's timestamp $$$t$$$; $$$L_{\\mathrm{in}}[i]$$$ is given, while $$$L_{\\mathrm{out}}[i]$$$ is unknown. </li><li> <span class=\"tex-font-style-bf\">TDN &lt;server&gt; &lt;task_spec&gt; &lt;dur&gt;</span> — a task completed and its server is now free. <span class=\"tex-font-style-bf\">task_spec</span> is echoed in a <span class=\"tex-font-style-bf\">canonical equivalent form</span>: integers use ordinary decimal notation and fields use single spaces; <span class=\"tex-font-style-bf\">dur</span> is the execution duration, <span class=\"tex-font-style-bf\">excluding</span> $$$S$$$, printed with 9 digits after the decimal point. </li><li> <span class=\"tex-font-style-bf\">XDN &lt;UP|DOWN&gt; &lt;remote&gt; &lt;size&gt; &lt;PRE|DEC&gt; &lt;m&gt; &lt;rid...&gt;</span> — a transfer completed (its data has arrived). <span class=\"tex-font-style-bf\">size</span> is in <span class=\"tex-font-style-bf\">bytes</span> ($$$= \\mathrm{len} \\times \\mathrm{bytes\\_per\\_token}$$$); <span class=\"tex-font-style-bf\">PRE</span>/<span class=\"tex-font-style-bf\">DEC</span> marks an input-stage or output-step transfer; per-remote computer transfers each produce their own <span class=\"tex-font-style-bf\">XDN</span>; for input stage, <span class=\"tex-font-style-bf\">m</span> $$$= 1$$$. The <span class=\"tex-font-style-bf\">m</span> request ids listed are exactly the requests whose data the transfer carries: the single request for input stage; that remote computer's members of the triggering <span class=\"tex-font-style-bf\">D PRE</span> for an output-step local-to-remote transfer; the members of the triggering <span class=\"tex-font-style-bf\">D PROC</span> group for an output-step remote-to-local transfer. </li><li> <span class=\"tex-font-style-bf\">FIN &lt;rid&gt;</span> — the request finished all output steps (its last token was just produced). It must not appear in any task you assign from now on. </li></ul><p><span class=\"tex-font-style-bf\">&lt;server&gt;</span> $$$=$$$ <span class=\"tex-font-style-bf\">E</span> (local computer) or <span class=\"tex-font-style-bf\">Ck</span> (remote computer $$$k$$$); <span class=\"tex-font-style-bf\">&lt;m&gt;</span> is the number of request ids that follow. request ids are integers $$$0, 1, \\dots, R-1$$$, assigned in arrival order, never reused.</p><p><span class=\"tex-font-style-bf\">Constraints</span></p><ul> <li> $$$1 \\le K \\le 8$$$; $$$1 \\le R \\le 2000$$$; $$$1 \\le L_{\\mathrm{in}}[i] \\le 4096$$$; $$$1 \\le L_{\\mathrm{out}}[i] \\le 512$$$; $$$\\sum_i L_{\\mathrm{out}}[i] \\le 2 \\cdot 10^{5}$$$ per test; $$$1 \\le \\mathit{num\\_layers} \\le 64$$$; $$$2 \\le N \\le 4096$$$. </li><li> $$$1 \\le S \\le 10$$$; $$$0.001 \\le \\mathrm{latency\\_in\\_ms} \\le 50$$$; $$$0.001 \\le \\mathrm{bandwidth\\_gbps} \\le 100$$$; $$$1 \\le \\mathrm{bytes\\_per\\_token} \\le 10^{6}$$$. </li><li> $$$0.001 \\le \\mathrm{SLO1},\\mathrm{SLO2} \\le 10^9$$$; $$$0 \\le tp_{\\mathrm{base}},dist_{\\mathrm{base}} \\le 10^9$$$; $$$10^{-9} \\le tp_{\\mathrm{UB}} \\le 10^9$$$; and $$$tp_{\\mathrm{UB}} \\gt tp_{\\mathrm{base}}$$$. </li><li> Every non-missing task-table entry is in $$$[0.001,10^4]$$$ ms. System reals, task times, timestamps, and durations use 9 decimal places. </li><li> Arrival timestamps are nondecreasing in $$$[0,10^9]$$$ ms. Completion frames may exceed $$$10^9$$$, but the validator guarantees a conservative upper bound of $$$10^{12}$$$ ms even if every legal task and transfer is serialized; all timestamps are nonnegative finite doubles. </li><li> <span class=\"tex-font-style-bf\">You never need to predict event timestamps</span> to keep the protocol correct: every completion is announced by the interactor (<span class=\"tex-font-style-bf\">TDN</span>/<span class=\"tex-font-style-bf\">XDN</span>) with its timestamp and duration, so a purely reactive scheduler needs no arithmetic on future times. If you simulate ahead for planning, use ordinary double-precision arithmetic with the piecewise-linear lookup and transfer formula above. </li><li> At most $$$2 \\cdot 10^{6}$$$ frames per test; use fast I/O. </li><li> Degenerate values (e.g. $$$K = 1$$$, $$$\\mathit{num\\_layers} = 1$$$) occur and simply disable the corresponding mechanic. </li></ul></div><div class=\"output-specification\"><div class=\"section-title\">Output</div><p>After every frame (one turn), print a count $$$n$$$ ($$$0 \\le n \\le K+1$$$), followed by $$$n$$$ assignments. For readability the examples put one assignment on each line, but the parser accepts arbitrary whitespace between tokens. Each assignment has the form <span class=\"tex-font-style-bf\">&lt;server&gt; &lt;task_spec&gt;</span>. It starts one task on a computer that is currently free. The command words shown below are fixed output syntax; copy them exactly. Integer tokens use the ordinary signed-decimal syntax accepted by C++ conversion (an optional leading <span class=\"tex-font-style-bf\">+</span> and leading zeros are accepted); echoed integers are canonical decimal. Thus a response containing no assignments is simply</p><pre class=\"verbatim\"><br/>0<br/></pre><p>For a first scheduler, most responses may contain only zero or one task. Unmentioned resources stay idle. You may leave any free computer idle even when one or more legal tasks are available. Waiting can be a useful grouping choice, but do not create the stuck state with no future event described in <span class=\"tex-font-style-bf\">Interaction</span>. Every frame is a scheduling opportunity, including frames containing only transfers or arrivals. After reading the whole frame, you may use any predecessor or free resource reported anywhere in it.</p><p>When deciding whether a task is legal, ask three questions: Is its computer free? Has every required predecessor event arrived? Is every request in the task at exactly this step and not already in flight or finished? The tables below make these checks precise.</p><p>All assignments in one response begin simultaneously at timestamp $$$t$$$. One cannot depend on another assignment from that same response. Assign at most one task to each resource; it becomes free again only when its <span class=\"tex-font-style-bf\">TDN</span> arrives. In <span class=\"tex-font-style-bf\">P PRE</span>, <span class=\"tex-font-style-bf\">&lt;remote&gt;</span> must be in $$$[0,\\, K)$$$; in <span class=\"tex-font-style-bf\">P PROC</span> and <span class=\"tex-font-style-bf\">P POST</span>, <span class=\"tex-font-style-bf\">&lt;remote&gt;</span> must equal the request's assigned remote computer — anything else is a violation. (<span class=\"tex-font-style-bf\">P POST</span> itself runs on the local computer: its <span class=\"tex-font-style-bf\">&lt;remote&gt;</span> field carries no scheduling meaning and is purely a consistency check against the request's fixed assignment.) Iteration indices are never transmitted: each request's steps are strictly sequential, so your own bookkeeping is the sole — and sufficient — source of truth for which iteration a task belongs to.</p><p>The <span class=\"tex-font-style-bf\">order</span> of request ids within a group has no semantic effect: legality, durations, transfer sizes, and all subsequent events depend only on the member <span class=\"tex-font-style-underline\">set</span> (<span class=\"tex-font-style-bf\">D PRE -1 3 4 7 9</span> and <span class=\"tex-font-style-bf\">D PRE -1 3 9 4 7</span> denote the same task). Order is preserved on echo: <span class=\"tex-font-style-bf\">TDN</span> repeats the same fields in canonical decimal form with single spaces, and every <span class=\"tex-font-style-bf\">XDN</span> lists its request ids in the order of the triggering task's specification — a <span class=\"tex-font-style-bf\">D PRE</span> group spanning remote computers has per-remote computer local-to-remote transfer lists that remote computer's members as a subsequence of your <span class=\"tex-font-style-bf\">D PRE</span> line, an output-step remote-to-local transfer lists the triggering <span class=\"tex-font-style-bf\">D PROC</span> group in your order.</p><p><span class=\"tex-font-style-bf\">Dependency Summary</span></p><p>Each task is listed separately so its predecessor and completion effect are easy to scan. For a group, the predecessor rule applies to every member.</p><ul> <li> <span class=\"tex-font-style-bf\">P PRE</span> — <span class=\"tex-font-style-bf\">Server:</span> local computer. <span class=\"tex-font-style-bf\">Requires:</span> the request's ARR event. <span class=\"tex-font-style-bf\">Completes:</span> fixes the request's remote computer and queues its input-stage local-to-remote transfer. </li><li> <span class=\"tex-font-style-bf\">P PROC piece</span> — <span class=\"tex-font-style-bf\">Server:</span> the assigned remote computer. <span class=\"tex-font-style-bf\">Requires:</span> for the first piece, the input-stage local-to-remote XDN; for a later piece, the previous piece's TDN. <span class=\"tex-font-style-bf\">Completes:</span> only the last piece ($$$le=\\mathit{num\\_layers}$$$) queues the input-stage remote-to-local transfer. </li><li> <span class=\"tex-font-style-bf\">P POST</span> — <span class=\"tex-font-style-bf\">Server:</span> local computer. <span class=\"tex-font-style-bf\">Requires:</span> the request's input-stage remote-to-local XDN. <span class=\"tex-font-style-bf\">Completes:</span> stops TDR and makes the request ready for output. </li><li> <span class=\"tex-font-style-bf\">D PRE</span> — <span class=\"tex-font-style-bf\">Server:</span> local computer. <span class=\"tex-font-style-bf\">Requires:</span> each member's previous final-step TDN (P POST or its previous D POST), and the request must not be finished. <span class=\"tex-font-style-bf\">Completes:</span> queues one local-to-remote transfer per remote computer represented in the group, in increasing remote-computer index. </li><li> <span class=\"tex-font-style-bf\">D PROC</span> — <span class=\"tex-font-style-bf\">Server:</span> the assigned remote computer. <span class=\"tex-font-style-bf\">Requires:</span> the local-to-remote XDN carrying each member's current-iteration data. <span class=\"tex-font-style-bf\">Completes:</span> queues one remote-to-local transfer whose length is the group size. </li><li> <span class=\"tex-font-style-bf\">D POST</span> — <span class=\"tex-font-style-bf\">Server:</span> local computer. <span class=\"tex-font-style-bf\">Requires:</span> the remote-to-local XDN carrying each member's current-iteration result. <span class=\"tex-font-style-bf\">Completes:</span> produces one token per member; after iteration $$$L_{\\mathrm{out}}[i]$$$, produces FIN. </li></ul></div><div><div class=\"section-title\">Interaction</div><p>Each test is a separate run of your program. <span class=\"tex-font-style-bf\">Flush the output stream after every response.</span> In C++, use <span class=\"tex-font-style-bf\">cout « flush;</span> after printing the complete response; we recommend <span class=\"tex-font-style-bf\">ios::sync_with_stdio(false); cin.tie(nullptr);</span> for fast input. In Python, call <span class=\"tex-font-style-bf\">sys.stdout.flush()</span> after printing the complete response (or use <span class=\"tex-font-style-bf\">print(..., flush=True)</span> for its final line).</p><p>The interaction proceeds: startup configuration (2 lines) $$$\\to$$$ Task-Time Table ($$$N+1$$$ lines) $$$\\to$$$ repeat $$$\\{$$$frame $$$\\to$$$ your response$$$\\}$$$ $$$\\to$$$ <span class=\"tex-font-style-bf\">END</span>. Your first response follows the first frame. The whole program follows this loop:</p><pre class=\"verbatim\"><br/>read the 2 parameter lines, then N and the N warmup rows<br/>loop:<br/>    read one line; if it is END: exit<br/>    parse it as timestamp t; read event count e from the next line<br/>    read the e event lines<br/>    update your state (completions, arrivals, transfers, FINs)<br/>    choose assignments for currently free resources (possibly none)<br/>    print n and the n assignment lines; flush<br/></pre><p>For a simple implementation, store one state per request. Its path is</p><pre class=\"verbatim\"><br/>ARR -&gt; P PRE -&gt; input stage UP -&gt; P PROC piece(s) -&gt; input stage DOWN -&gt; P POST<br/>    -&gt; D PRE -&gt; output UP -&gt; D PROC -&gt; output DOWN -&gt; D POST<br/>    -&gt; either FIN or the next D PRE<br/></pre><p>Move a request to its next state only when the corresponding event appears in a frame. Mark a computer busy when you assign it and free only when its <span class=\"tex-font-style-bf\">TDN</span> appears. Tracking these states is enough for a correct solution. You do not need to predict when tasks will finish.</p><p><span class=\"tex-font-style-bf\">You act only when a frame arrives.</span> There is no timer or self-wake mechanism: you cannot ask to be woken at a chosen future time, and you cannot deliberately idle a computer until an arbitrary moment. A task can only be assigned in response to a frame, at that frame's timestamp. If you delay an action, you must wait for a future event frame.</p><p><span class=\"tex-font-style-bf\">Mistakes That Give Zero Points on a Test</span></p><p>The following errors score $$$0$$$ on the test. A legal but slow choice is still valid; it only lowers your score.</p><ul> <li> Assigning a task to a busy computer, or two tasks to one resource in a single response. </li><li> Assigning a task before all of its required earlier events have been delivered. This includes referencing a rid that has not arrived and re-issuing a completed step. </li><li> Including a request that is already part of an in-flight task, or that has already finished (<span class=\"tex-font-style-bf\">FIN</span>). </li><li> Wrong remote computer: <span class=\"tex-font-style-bf\">P PROC</span>/<span class=\"tex-font-style-bf\">P POST</span> with a remote computer other than the request's assigned remote computer; <span class=\"tex-font-style-bf\">P PRE</span> with a remote computer outside $$$[0, K)$$$; a <span class=\"tex-font-style-bf\">D PROC</span> member assigned to a different remote computer. </li><li> Illegal piece: empty ($$$ls = le$$$), outside $$$[0, \\mathit{num\\_layers}]$$$, or not ascending and gap-free. </li><li> Malformed group: $$$m  \\lt  1$$$ or duplicate request ids. </li><li> Malformed or unparsable output. </li><li> Reaching a stuck state with unfinished requests and no possible future event (see below). </li><li> Exceeding the time or memory limit. </li></ul><p><span class=\"tex-font-style-bf\">Errors and stream closure</span></p><p>The interactor never produces <span class=\"tex-font-style-bf\">-1</span> as a failure response. This is unrelated to the mandatory <span class=\"tex-font-style-bf\">-1</span> marker in participant commands <span class=\"tex-font-style-bf\">D PRE</span> and <span class=\"tex-font-style-bf\">D POST</span>. On a protocol violation or malformed response it simply stops: the test scores $$$0$$$ and no further frames are sent. If reading input ever fails or reaches end-of-file, exit immediately with exit code $$$0$$$ — do not block waiting for more input and do not crash; the verdict is determined by the interactor, not by your exit path.</p><p><span class=\"tex-font-style-bf\">Getting Stuck</span></p><p>If unfinished requests remain but no task, transfer, or future arrival can create another event, the run is stuck. The interactor detects this stuck state, terminates, and assigns $$$0$$$ to the test. While future arrivals remain, responding with $$$0$$$ assignments is safe because time advances to the next arrival. Delaying a request hurts the score; permanently abandoning it can cause this stuck state.</p><p><span class=\"tex-font-style-bf\">Termination</span></p><p>When all requests have finished, the interactor sends <span class=\"tex-font-style-bf\">END</span> (a single line, in place of the next frame's header) after reading your response to the final frame. Read it and exit.</p><p>The total number of requests $$$R$$$ is not announced in advance and there is no \"no more arrivals\" signal — you cannot distinguish a lull from the end of the stream. This is intentional; plan your grouping accordingly.</p></div><div><div class=\"section-title\">Scoring</div><p>You do not need to calculate the score to write a valid scheduler. First make a scheduler that finishes every request legally. Read the formula only when you are ready to improve its score. It balances two intuitive goals:</p><ul> <li> <span class=\"tex-font-style-bf\">Output rate</span>: finish more output tokens per millisecond of simulated time. </li><li> <span class=\"tex-font-style-bf\">waiting time</span>: make requests ready for output promptly and avoid long gaps between produced tokens. </li></ul><p>Each goal becomes a component in $$$[0,1]$$$. The weights $$$w_{\\mathrm{tp}}$$$ and $$$w_c$$$ say how much that test values each goal, and the final score is their weighted sum times $$$1000$$$.</p><p>The exact guarantees are: $$$w_{\\mathrm{tp}}, w_c \\ge 0$$$; $$$w_{\\mathrm{tp}} + w_c = 1$$$; $$$\\mathrm{SLO1}  \\gt  0$$$; $$$\\mathrm{SLO2}  \\gt  0$$$; $$$tp_{\\mathrm{UB}}  \\gt  tp_{\\mathrm{base}}$$$; $$$dist_{\\mathrm{base}} \\ge 0$$$. Either weight may be $$$0$$$, but every request must still be completed and every input/output rule obeyed. The following formula turns a value into a number from $$$0$$$ to $$$1$$$:</p><p>$$$$$$\\mathsf{clamp}(x;\\, \\mathit{base},\\, \\mathit{target}) = \\max\\bigl(0,\\, \\min\\bigl(1,\\, (x - \\mathit{base})/(\\mathit{target} - \\mathit{base})\\bigr)\\bigr)$$$$$$</p><p>($$$0$$$ at $$$\\mathit{base}$$$, $$$1$$$ at $$$\\mathit{target}$$$, clamped outside).</p><p><span class=\"tex-font-style-bf\">Output-Rate Component.</span> $$$\\mathit{tp} = \\sum_i L_{\\mathrm{out}}[i] \\,/\\, \\text{total elapsed time}$$$ tokens/ms, where total elapsed time $$$=$$$ (the latest final-token production time over all requests) $$$-$$$ (the earliest request arrival time), in ms. Output rate component $$$= \\mathsf{clamp}(\\mathit{tp};\\, tp_{\\mathrm{base}},\\, tp_{\\mathrm{UB}})$$$. The value $$$tp_{\\mathrm{base}}$$$ comes from a fixed one-request-at-a-time reference schedule; $$$tp_{\\mathrm{UB}}$$$ is an estimated high rate. At or below the baseline the component is $$$0$$$; at or above the upper bound it is $$$1$$$; between them it grows linearly. These values set scoring and are not promises about any solution in the testing kit.</p><p><span class=\"tex-font-style-bf\">Waiting-Time Component.</span> The input gives two waiting-time targets. <span class=\"tex-font-style-bf\">SLO1</span> is the target average wait until a request is ready for its first output step (time to decode ready, TDR). No token has been produced at this point. <span class=\"tex-font-style-bf\">SLO2</span> is the target mean gap between consecutive produced tokens (TPOT). The letters <span class=\"tex-font-style-bf\">SLO</span> are only part of the fixed input names. For request $$$i$$$, let $$$e_1  \\lt  e_2  \\lt  \\dots  \\lt  e_{L_{\\mathrm{out}}[i]}$$$ be its token production times, i.e. the completion times of its output <span class=\"tex-font-style-bf\">D POST</span> tasks.</p><ul> <li> $$$\\mathit{tdr}$$$ $$$=$$$ mean over all requests of (input stage final step completion $$$-$$$ arrival). </li><li> $$$\\mathit{tpot}$$$ $$$=$$$ mean of $$$e_{j+1} - e_j$$$ over all consecutive output gaps of all requests pooled ($$$1 \\le j  \\lt  L_{\\mathrm{out}}[i]$$$). A request with $$$L_{\\mathrm{out}}[i] = 1$$$ contributes no gaps. If no request contributes a gap, $$$\\mathit{tpot}$$$ is defined as $$$0$$$. </li></ul><p>$$$$$$\\mathit{excess\\_tdr} = \\max\\Bigl(0,\\, \\frac{\\mathit{tdr} - \\mathrm{SLO1}}{\\mathrm{SLO1}}\\Bigr), \\quad \\mathit{excess\\_tpot} = \\max\\Bigl(0,\\, \\frac{\\mathit{tpot} - \\mathrm{SLO2}}{\\mathrm{SLO2}}\\Bigr),$$$$$$ $$$$$$\\mathit{dist} = \\sqrt{\\mathit{excess\\_tdr}^{2} + \\mathit{excess\\_tpot}^{2}}.$$$$$$</p><p>waiting-time component $$$= \\mathsf{clamp}(\\mathit{dist};\\, dist_{\\mathrm{base}},\\, 0)$$$ — the same conversion with lower values treated as better: lower $$$\\mathit{dist}$$$ is better, $$$1$$$ at $$$\\mathit{dist} = 0$$$, $$$0$$$ at the reference scheduler's amount above the waiting-time targets $$$dist_{\\mathrm{base}}$$$. Written out directly (the form easiest to implement and verify):</p><p>$$$$$$\\text{waiting-time component} \\;=\\; \\begin{cases} \\max\\bigl(0,\\; 1 - \\mathit{dist}/dist_{\\mathrm{base}}\\bigr) &amp; \\text{if } dist_{\\mathrm{base}}  \\gt  0,\\\\ 1 &amp; \\text{if } dist_{\\mathrm{base}} = 0 \\text{ and } \\mathit{dist} = 0,\\\\ 0 &amp; \\text{if } dist_{\\mathrm{base}} = 0 \\text{ and } \\mathit{dist}  \\gt  0. \\end{cases}$$$$$$</p><p><span class=\"tex-font-style-bf\">Important special case:</span> if $$$dist_{\\mathrm{base}} = 0$$$, the waiting-time component is either $$$0$$$ or $$$1$$$. It is $$$1$$$ only when both mean-waiting-time targets are met ($$$\\mathit{dist}=0$$$), and $$$0$$$ otherwise.</p><center> <img class=\"tex-graphics\" src=\"https://espresso.codeforces.com/4b7de63addc1956e540aff68b67201c830cc1e1d.png\" style=\"max-width: 100.0%;max-height: 100.0%;\" width=\"605px\"/> </center><p><span class=\"tex-font-style-it\">Diagram guide:</span> the upper branch rewards higher output rate; the lower branch rewards smaller normalized TDR/TPOT target violations. The two $$$[0,1]$$$ components are weighted, added, and multiplied by $$$1000$$$.</p><p>$$$\\mathsf{NormalizedScore} = w_{\\mathrm{tp}} \\cdot \\mathsf{clamp}(\\mathit{tp};\\, tp_{\\mathrm{base}},\\, tp_{\\mathrm{UB}}) + w_c \\cdot \\mathsf{clamp}(\\mathit{dist};\\, dist_{\\mathrm{base}},\\, 0),$$$ $$$\\mathsf{Score} = 1000 \\cdot \\mathsf{NormalizedScore}.$$$</p><p>Thus each completed test awards a score in $$$[0, 1000]$$$. <span class=\"tex-font-style-bf\">Verdicts.</span> A completed interaction scores as above. A protocol error, malformed output, stuck state with no future event, or exceeding the time/memory limit scores $$$0$$$ on that test; other tests are unaffected. No partial credit is awarded for an unfinished test.</p><p><span class=\"tex-font-style-bf\">Contest aggregation.</span> The 22 preliminary tests provide feedback and do not contribute to the final ranking. The final score is the arithmetic mean of the 20 frozen final-test scores. Ranking uses that mean before display rounding; the displayed score is rounded to three digits after the decimal point. Therefore a known per-test vector of $$$0$$$, $$$500$$$, and $$$1000$$$-point outcomes contributes exactly those values before averaging.
